# 課題2の実装ステップ

## 1. AI と作業するための準備

- リポジトリ直下に `AGENTS.md` を用意し、参照資料、作業範囲、完了条件の確認方法を記載する。
- 生成コードを変更する場合は、OpenAPI や SQL などの生成元を編集して再生成する方針を記載する。起動・テスト・コード生成のコマンドは、使えるようになった段階で README に追記し、`AGENTS.md` から参照できるようにする。
- **完了条件** `AGENTS.md` から要件と設計を参照でき、ステップごとの進め方が分かる。

## 2. 開発・テスト環境

- `compose.yaml` に開発用の Gin サーバーを追加し、既存の MySQL と一緒に起動する。開発サーバーは HTTP で起動し、ソースをマウントして Air で監視する。
- 起動確認用の `GET /healthz` を OpenAPI で定義し、`oapi-codegen` で Gin 用のコードを `api/` に生成する。
- `GET /healthz` のユニットテストと `httptest` を使う HTTP テストを整える。同じ MySQL コンテナに、後続の HTTP テストで使うテスト用 DB を作成する。
- リモートリポジトリを用意し、CI で `go test`、`golangci-lint`、`actionlint` を実行する。golangci-lint では、日本語のデータを扱うため `gosmopolitan` を除く全リンターを有効にし、Go コードのフォーマットも確認する。
- **完了条件** `docker compose up` で開発環境が起動し、Go ファイルの変更で API が再ビルド・再起動する。両方のテストをローカルで実行でき、CI の3つのチェックが通る。

## 3. API 仕様とルーティング

- 既存の OpenAPI 定義に `GET /students` のクエリとレスポンスを追加し、`oapi-codegen` で Gin 用のコードを再生成する。ハンドラーを仮の取得処理につなぐ。
- 起動確認用の `GET /healthz` と関連テストを削除し、`GET /students` の HTTP テストでルーティングを確認する。
- **完了条件** `httptest` でレスポンスの形式を確認できる。`facilitator_id` が指定されていない場合や型が不正な場合は、本文なしの `400` が返ることを確認できる。

## 4. MySQL から生徒一覧を取得

- `sqlc` でデータアクセスコードを生成し、ハンドラー、ユースケース、リポジトリ、MySQL をつなぐ。教師 ID で絞り込み、クラス情報と `totalCount` を返す。
- テスト用 MySQL を使う HTTP テストを追加し、ローカルと CI の両方で実行する。
- **完了条件** 初期データで `facilitator_id=1` を指定すると、生徒 ID `1, 4, 7, 10` が ID の昇順で返り、`totalCount` が `4` になる。該当する生徒がいない場合は本文なしの `404` が返る。CI でユニットテストと HTTP テストが通る。

## 5. 検索

- `name_like` と `loginId_like` の部分一致を実装する。両方を指定した場合は AND 条件にする。
- **完了条件** 各検索条件と AND 検索をテストし、絞り込み後の件数が `totalCount` に反映されることを確認できる。検索で絞り込んだ結果が 0 件の場合にも、本文なしの `404` が返ることを確認できる。

## 6. ソート

- `sort` と `order` を実装する。既定値は `id` と `asc` とし、生徒名が同じ場合は生徒 ID の昇順で並べる。
- **完了条件** `id`、`name`、`loginId` の昇順・降順、同名時の順序、不正なソート指定に対する本文なしの `400` を確認できる。

## 7. ページネーション

- `page` と `limit` を実装する。既定値は `1` と `5` とし、`totalCount` にはページ分割前の該当件数を返す。
- **完了条件** 次の動作を確認できる。
  - パラメーターを省略すると、既定値でページ分割する。
  - 不正値に対して、本文なしの `400` を返す。
  - 該当件数があっても指定ページが範囲外なら、空配列と `totalCount` を含む `200` を返す。
  - 検索とソートを併用した場合は、絞り込んで並べた結果から指定ページを返す。

## 8. 通常起動と HTTPS

- `compose.yaml` では、静的ビルドした API バイナリを `scratch` イメージで実行する。Air とソースのマウントは `compose.dev.yaml` に移す。
- ローカル用の自己署名証明書の自動生成と MySQL の起動待ちを組み込む。通常起動と開発起動で MySQL と TLS の設定を共通にする。
- README に起動、証明書を検証して接続する方法、テストの実行手順を記載する。
- **完了条件** `docker compose up` と開発用の Compose 構成の両方で起動し、`curl --cacert` で `https://127.0.0.1:48080/students?facilitator_id=1` に接続できる。

## 9. 教師の命名を統一

- 教師を表す英語の命名を `facilitator` に統一する。コード、DB のテーブル名などの識別子、ドキュメントの記述を対象とする。
- **完了条件** 対象範囲で教師を表す英語の名称が `facilitator` に統一されている。

## 10. API のログを追加

- HTTP リクエストのメソッド、パス、レスポンスのステータス、処理時間を記録する。クエリ文字列とリクエスト・レスポンスの本文は記録しない。
- サーバー側のエラーは原因をログに記録し、クライアントには本文なしのエラーレスポンスを返す。
- **完了条件** リクエストの処理結果と、サーバー側で発生したエラーの原因をログで確認できる。
