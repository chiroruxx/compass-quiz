# 実装ステップのレビュー

1. 対象ステップと `docs/tasks/2_api/steps.md` の完了条件を特定する。比較元を確認し、対象ステップのコード差分（コミット済み・ステージ済み・未ステージ・未追跡）を把握する。レビューと修正の対象はソースコードとテストコードに限る。要件書や設計書などは判断の根拠として参照する。対象のコード差分がなければ、このスキルのレビューは省略する。
2. 下表の各観点を別々のサブエージェントに割り当てる。各エージェントには同じレビュー範囲、完了条件、関連する要件・設計への参照を渡し、担当する観点から変更を確認するよう依頼する。レビュー中のファイル編集は行わない。
3. サブエージェントは非同期で起動する。各結果を待たずに4件の割り当てを試みる。同時実行枠が足りない場合は、完了したエージェントの結果を回収して枠を空け、残りの観点を新しいエージェントに割り当てる。
4. 4件の結果を受け取り、重複する指摘をまとめて、差分と要件に照らして妥当性を確認する。修正方針が明確で対象範囲内の指摘は親エージェントが修正し、関連するテストや完了条件を再確認する。
5. 人間の判断が必要な指摘は、重要度の高い順に、該当箇所、影響、判断してほしい点を報告する。修正した内容と検証結果も共有する。結果が揃わない場合や判断に必要な検証が残る場合は、レビューを未完了とし、その理由を伝える。人間のレビューに渡す手順は `AGENTS.md` に従う。

| 観点 | 確認内容 |
| --- | --- |
| 正確さ | 完了条件を一つずつ照合し、変更内容とテスト結果が各条件を満たすか確認する。 |
| 簡潔さ | 完了条件に対して実装が過剰になっていないか、早期リターンなどで制御フローを単純にできるか、処理が責務に合ったレイヤーに置かれているか確認する。 |
| 堅牢さ | 変更によって生じるセキュリティリスクを確認する。指摘には影響を受ける処理とリスクを軽減する修正案を挙げる。 |
| 可読性 | コード内のコメントと命名が意図を伝えるか確認する。型名の流用で役割が伝わりにくい箇所では、ドメイン上の意味や責務が分かる名前を提案する。 |

各エージェントは、指摘ごとに重要度、ファイルと行、根拠、影響、修正案を返す。指摘がなければその旨を、確認できない項目があれば対象と理由を返す。
